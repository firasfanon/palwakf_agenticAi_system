# دستور وكلاء PalWakf المحليين

**الإصدار:** 0.1 — تأسيسي  
**الحالة:** مسودة حاكمة قابلة للاعتماد بعد مطابقتها مع `PALWAKF_PLATFORM_COMPREHENSIVE_GUIDE.md`  
**الغرض:** ضبط عمل فريق المساعدين والوكلاء المحليين بحيث يساعد في تطوير PalWakf دون تجاوز السيادة، الصلاحيات، أو النسخ المستقرة.

---

## 1) الهدف

فريق الوكلاء ليس بديلًا عن صاحب القرار. هدفه تقليل العمل المتكرر، تنظيم التحليل والبناء والاختبار، وحماية المنصة من التعديلات العشوائية.

كل وكيل يعمل ضمن وظيفة محددة، وأدوات محددة، وصلاحيات محدودة، ومخرجات قابلة للفحص.

---

## 2) مبادئ غير قابلة للتجاوز

1. **الصراحة:** يميّز الوكيل بين نتيجة مثبتة، واحتمال، ومعلومة غير متاحة.
2. **مصدر الحقيقة أولًا:** لا يبدأ تعديل أو تشخيص قبل تحديد مصدر الحقيقة ومسار القراءة ومسار الكتابة.
3. **سيادة المخططات:** `core` و`waqf` والمخططات النظامية المتخصصة هي مصادر البيانات السيادية بحسب المجال. لا يستخدم `public` مصدرًا للبيانات السيادية أو التشغيلية.
4. **دور `public`:** مسموح فقط كواجهة عرض مشتقة أو دالة مغلفة ومضبوطة، مثل View أو RPC wrapper، مع التصريح بالمصدر السيادي خلفه.
5. **لا وصول تلقائي إلى الإنتاج:** لا يحق لأي وكيل تطبيق SQL حساس، دمج تغييرات في الفرع الرئيسي، أو نشر إنتاجي دون موافقة صريحة من المستخدم.
6. **أقل صلاحية ممكنة:** يمنح كل وكيل أقل أدوات وصلاحيات تكفي لمهمته.
7. **دفعات مركزة:** لا تُحوَّل التعديلات الصغيرة إلى مشاريع منفصلة. تجمع ضمن دفعة مركزة ذات هدف واحد واضح.
8. **أدلة مختصرة:** دليل رئيسي واحد، وملف مخرجات داعم عند الحاجة فقط.
9. **لا نجاح بلا تحقق:** لا يعلن الوكيل أن العمل مغلق قبل وجود دليل مناسب وتحديث ملفات الحالة.
10. **العربية أولًا:** يشرح الوكيل هدف كل إجراء بالعربية، ويعرّف أي مصطلح إنجليزي عند أول استخدام.

---

## 3) قواعد البيانات والحدود المعمارية

| المجال | المصدر السيادي أو التشغيلي | دور `public` |
|---|---|---|
| الوحدات التنظيمية | `core.org_units` | View أو RPC فقط عند الحاجة |
| الأصول الوقفية | `waqf_assets` والمسار الوقفي المعتمد | View أو RPC فقط عند الحاجة |
| المحتوى والإعلام | `media_center` | View أو RPC فقط عند الحاجة |
| الصفحات والتجربة العامة | `platform_experience` | View أو RPC فقط عند الحاجة |
| المعرفة والمساعدة | `assistant` | View أو RPC فقط عند الحاجة |
| المالية والدفع | `billing_system` | View أو RPC فقط عند الحاجة |
| القضايا | `cases`، مع التوجه إلى `legal_system` | View أو RPC فقط عند الحاجة |
| المهام | `tasks` | View أو RPC فقط عند الحاجة |
| التحليل المكاني والتاريخي | `mustakshif` | ليس مصدر تشغيل للأصول |

**قاعدة مركزية:** `waqf_assets` هو الكيان التشغيلي المركزي، والربط التشغيلي يجب أن يستخدم `waqf_asset_id` عند انطباقه.

---

## 4) نموذج دورة العمل

```text
طلب المستخدم
→ تحليل وتخطيط
→ مراجعة سيادة وبيانات
→ تصميم واجهة عند الحاجة
→ بناء في نسخة عمل معزولة
→ اختبار وتحقق
→ توثيق وتسليم
→ اعتماد المستخدم
```

لا يعمل أكثر من وكيل كتابة على الملفات نفسها في الوقت نفسه.

---

## 5) بوابة البدء الإلزامية

قبل كل مهمة، يجب على الوكيل المسؤول أن يكتب بالعربية:

- الهدف العملي من المهمة.
- نوع العمل: تطوير، إصلاح، فحص، حوكمة، أو توثيق.
- مصدر الحقيقة.
- مسار القراءة والكتابة المتوقع.
- ما الذي لا يجوز تغييره.
- هل ظهر `public`؟ وإن ظهر، هل هو View أو RPC فقط وما مصدره السيادي؟
- دليل النجاح المطلوب.

إذا تعذر تحديد هذه العناصر، تتوقف المهمة وتتحول إلى فحص مرجعي محدود، لا إلى تخمين أو توسع في التعديل.

---

## 6) بروتوكول معالجة الأخطاء

1. تصنيف الخطأ: بناء، تشغيل، بيانات، صلاحيات، واجهة، بيئة، أو معمارية.
2. تحديد أقل حالة يمكن إعادة الخطأ فيها.
3. فرضية واحدة → تعديل واحد → اختبار واحد → نتيجة موثقة.
4. بعد 60–90 دقيقة بلا دليل جديد، ينشأ سجل خطأ مختصر بدل الاستمرار في تجارب عشوائية.
5. الخيارات المسموحة عند التوقف: عزل المشكلة، الرجوع إلى نسخة مستقرة، بناء اختبار صغير مستقل، إعادة تصميم المسار، أو تأجيل رسمي مع مانع واضح.

---

## 7) متطلبات الإغلاق والتسليم

لا تُغلق دفعة إلا بعد:

- تحديث ملف الحالة أو المرجع عند تغير واقع المنصة.
- تسجيل ما تغيّر وما تم التحقق منه وما بقي مفتوحًا.
- حفظ نسخة مرجعية مستقرة عند نجاح الدفعة.
- إعداد تسليم مرحلي واضح للجلسة التالية.
- تجميع ملفات الدفعة عند الحاجة دون تكثير ملفات الأدلة.

---

## 8) حدود السلامة التشغيلية

- لا تعطيل لقواعد الحماية في قاعدة البيانات لتجاوز خطأ.
- لا إنشاء جداول جديدة في `public` لتفادي مشكلة في مصدر سيادي.
- لا استخدام `dynamic` أو fallback غير مبرر لإسكات خطأ برمجي.
- لا تعديل مباشر على بيئة الإنتاج.
- لا اعتبار قراءة واجهة عرض دليلًا على سلامة مصدر البيانات دون معرفة المصدر خلفها.
